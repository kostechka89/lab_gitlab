# Общий текст защиты

Порядок: Костя → Дима → Лариса → Настя → Костя. Основной рассказ занимает примерно 5–7 минут без вопросов. Текст описывает устройство готовой работы; личный вклад называйте только по фактически выполненным действиям.

## 1. Костя — начало и общая инфраструктура

«В этой работе мы подготовили CI/CD-среду в GitLab для четырёх разных приложений. GitLab и Runner у нас общие, а у каждого участника отдельный проект, репозиторий и pipeline.

Я настраивал общую среду на своём Windows-компьютере и загружал проекты. GitLab запущен в Docker через Docker Compose. В этом же Compose запущен GitLab Runner. Данные GitLab и настройки Runner сохраняются в Docker volumes, поэтому после остановки и повторного запуска они остаются.

GitLab хранит исходники и управляет pipeline. Runner получает задания от GitLab и выполняет их. Мы выбрали Docker executor: для каждого job создаётся отдельный контейнер Python. Наш Runner сейчас можно проверить на странице администрирования. Один Runner обслуживает все четыре проекта, а результаты у проектов остаются отдельными.

В каждом репозитории есть файл .gitlab-ci.yml. В нём три последовательных этапа: build, test и deploy. Pipeline — весь процесс, stage — этап этого процесса, а job — конкретное задание с командами. После push GitLab создаёт pipeline, а Runner выполняет эти задания».

**Показ:** группа с четырьмя проектами, Runner Online, затем YAML Todo API. Про текущий Online говори после проверки экрана.

## 2. Костя — Todo API и объяснение CI

«Мой индивидуальный проект — API задач. Он позволяет создать задачу, получить список, отметить задачу выполненной и удалить её. Запросы идут по HTTP, ответы возвращаются в JSON. Задачи хранятся в памяти, поэтому после перезапуска список очищается.

Вот пример: создаю задачу, получаю её ID, показываю список, отмечаю выполнение и удаляю запись.

Теперь покажу CI на этом проекте. На build Python проверяет компиляцию исходника, а затем создаётся ZIP-пакет. Этот файл сохраняется как artifact. На test запускаются четыре настоящих unittest-теста: они проверяют операции над задачами, названия и уникальность ID. Ещё запускается smoke-проверка: приложение берётся из ZIP, запускается HTTP-сервер и к нему отправляются реальные запросы.

На deploy тот же ZIP распаковывается в папку deploy. Приложение снова проверяется, затем создаётся манифест с SHA256 файлов. Это учебный deployment: результат — проверенный пакет приложения, а не постоянно работающий production-сервис.

Вот успешный pipeline и логи заданий. Если тест завершится ошибкой, test_job упадёт, и deploy не начнётся. Команда test действительно запускает тесты, а не просто печатает сообщение об успехе.

У остальных проектов схема CI такая же, но приложения и проверки другие. Дима покажет планировщик заданий».

**Показ:** API-запросы, tests/test_app.py, pipeline #6, jobs build #16, test #17, deploy #18 и artifacts. Это IDs из сохранённой проверенной версии; при появлении новых commits показывайте pipeline соответствующего commit.

## 3. Дима — Student Planner

«Мой проект — веб-планировщик учебных заданий. В браузере можно указать предмет и название задания, добавить его, отметить выполненным и удалить.

Показываю добавление: задание появляется со статусом Pending. После кнопки complete статус становится Completed, а delete удаляет запись.

Приложение написано на Python. Сервер принимает данные HTML-форм, изменяет список заданий и возвращает страницу. Пользовательский текст экранируется, чтобы его не интерпретировать как HTML. Данные также хранятся в памяти.

У меня три автоматических теста: жизненный цикл задания, проверка обязательных полей и экранирование текста. Дополнительно smoke отправляет настоящие HTTP-формы к запущенному приложению из ZIP.

Вот отдельный репозиторий, CI-конфигурация и успешный pipeline. В test_job видны три выполненных теста и проверка запуска.

В моём проекте данные вводятся через браузер. У Ларисы вход — CSV-файл, а результат — HTML-отчёт».

**Показ:** приложение на localhost:8002, тесты, pipeline #7 и test job #20.

## 4. Лариса — CSV Sales Report

«Мой проект обрабатывает CSV с продажами и создаёт HTML-отчёт. В таблице три поля: товар, количество и цена. Программа умножает количество на цену, объединяет продажи одинаковых товаров и вычисляет общий итог.

Показываю исходный sample.csv, запускаю программу и открываю report.html. Для нашего примера общий итог — 24.70.

Для денежных расчётов используется Decimal, чтобы не получать погрешности обычных дробных чисел. Программа проверяет заголовок CSV и значения: название не должно быть пустым, количество и цена не должны быть отрицательными.

Четыре теста проверяют расчёты, некорректные данные, заголовок, пустую таблицу и экранирование названий в HTML. Smoke запускает программу из собранного ZIP и проверяет созданный отчёт.

Вот мой отдельный pipeline и лог test_job с четырьмя тестами. На deploy сохраняется проверенный пакет программы.

Моя программа обрабатывает таблицу продаж. Настя покажет консольный анализ текста».

**Показ:** sample.csv, report.html, тест расчёта, pipeline #9 и test job #26.

## 5. Настя — Text Analyzer

«Мой проект — консольный анализатор текста. Он читает UTF-8 файл или стандартный ввод и выводит JSON: число символов, строк, слов, уникальных слов и пять самых частых слов.

Вот sample.txt и результат запуска. В примере три слова, из них два уникальных. Перед подсчётом слова приводятся к нижнему регистру, поэтому Hello и hello считаются одним словом.

Для выделения слов используется регулярное выражение, для уникальных слов — set, для частот — Counter. Если файл не удалось прочитать, программа показывает ошибку и возвращает код 2.

У меня четыре теста: они проверяют подсчёт, пустой текст, русский текст и пунктуацию. Smoke дополнительно запускает CLI с файлом и со стандартным вводом, а затем проверяет JSON.

Вот отдельный репозиторий и успешный pipeline. В логе test_job видны реальные результаты четырёх тестов. Передаю слово Косте».

**Показ:** sample.txt, команда запуска и JSON, тесты, pipeline #8 и test job #23.
